# PLAN — 自优化小红书工作流（执行计划）

> 2026-09-27 起草。账号：新号（2026-09 注册，0 笔记）。Chris 不写 Jev 代码，由 Claude 主导实现。

## 核心思路
照搬 TypeSafe「autoresearch feature discovery」cookbook 的闭环：
Claude 提出判断问题 → Jev 把笔记文本转成数值特征 → 简单模型（CatBoost / 线性）预测互动 → 读预测误差最大的样本 → Claude 改问题 / 改写作指南 → 再来一轮。
Jev 只做判断（打分 / 是否），抓取、计算、发布都由代码完成，写作交给 Claude。

## 阶段与关卡

| --- | --- | --- |
| 0 基建 | MCP 登录新号；TypeSafe key；Python 项目 + SQLite | `check_login_status` 正常，Jev 能跑通一次调用 |
| 1 离线验证 | 在所选赛道抓 300–500 篇笔记（包括低互动的，不只看爆款）+ 作者粉丝数；Claude 出约 20 个问题；Jev 打分；训练模型预测 log(互动) | 留出集上，Jev 特征的效果要**明显好于**只用粉丝数 / 字数的基线。不达标 = Jev 在这个赛道没用，不进入下一阶段 |

## 设计要点
- **自我验证**：大约 20% 的发布名额留给「非 Top」草稿（随机探索）。如果只发高分稿，就永远无法验证排序到底对不对。
- **混杂因素**：别人笔记的互动主要受作者粉丝数影响，所以要把粉丝数作为控制变量，或者对它做归一化。
- **Jev 的中文能力**：官方说明英文最好，CJK 能用但效果较弱。阶段 1 就是为了验证这一点。
- **配图**：`publish_content` 至少需要 1 张图。Claude 不会画图，所以用 HTML 模板渲染文字卡片（Playwright 截图），可以全自动完成。
- **账号安全**：新号先完成实名认证；每天发 1–2 篇（不照搬 MCP 作者说的 50 篇）；不引流、不搬运；按规定标注 AI 生成内容。
- **登录冲突**：MCP 登录新号之后，Chrome 网页版不要再登录这个号（否则会互相踢下线），看数据用手机 App。

## 餐厅评估器（赛道带来的新增模块）
- 抓取由代码完成，Jev 只判断。每条评价要回答：是否在说这家店（Noul）、是否像软广 / 探店广告（Noul）、口味 / 服务 / 性价比 / 环境各维度的评价（Score）、提到的招牌菜（从候选里选）
- 星级、评价数、时间新旧、跨来源加权，全部在代码里算（Jev 不擅长数字和日期比较）
- 数据来源优先走官方 API：Google Places、Yelp Fusion、TripAdvisor Content API（每家店通常只返回 3–5 条评价，具体配额和费用 [需核实]）、Reddit API；小红书用 MCP 的 `search_feeds` 和 `get_feed_detail`
- 不抓 Google / Yelp / TripAdvisor 的网页（违反服务条款，Yelp 还有起诉爬虫的先例）
- 笔记里不照搬别人的评价原文和照片（版权），用自己的话概括
