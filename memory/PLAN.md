## 核心思路
照搬 TypeSafe「autoresearch feature discovery」cookbook 的闭环：
Claude 提出判断问题 → Jev 把笔记文本转成数值特征 → 简单模型（CatBoost / 线性）预测互动 → 读预测误差最大的样本 → Claude 改问题 / 改写作指南 → 再来一轮。
Jev 只做判断（打分 / 是否），抓取、计算、发布都由代码完成，写作交给 Claude。

## 设计要点
- **自我验证**：大约 20% 的发布名额留给「非 Top」草稿（随机探索）。如果只发高分稿，就永远无法验证排序到底对不对。
- **混杂因素**：别人笔记的互动主要受作者粉丝数影响，所以要把粉丝数作为控制变量，或者对它做归一化。
- **Jev 的中文能力**：官方说明英文最好，CJK 能用但效果较弱。阶段 1 就是为了验证这一点。
- **配图**：`publish_content` 至少需要 1 张图。Claude 不会画图，所以用 HTML 模板渲染文字卡片（Playwright 截图），可以全自动完成。
- **账号安全**：新号先完成实名认证；每天发 1–2 篇（不照搬 MCP 作者说的 50 篇）；不引流、不搬运；按规定标注 AI 生成内容。
- **登录冲突**：MCP 登录新号之后，Chrome 网页版不要再登录这个号（否则会互相踢下线），看数据用手机 App。

## 餐厅评估器（赛道带来的新增模块）
- 抓取由代码完成，Jev 只判断。每条评价要回答：是否在说这家店（Noul）、是否像软广 / 探店广告（Noul）、口味 / 服务 / 性价比 / 环境各维度的评价（Score）、提到的招牌菜（从候选里选）
- 星级、评价数、时间新旧、跨来源加权，全部在代码里算（Jev 不擅长数字和日期比较）
- 数据来源（2026-09-27 提案，全部写成代码，不通过网页操纵其他 AI）：
  - Google：Playwright 无头浏览器，**不登录**，每天只抓几家店，每家约 50 条（按「最新」排序），另外读星级分布直方图；遇到验证码就跳过这家店并记日志，**不绕过**。违反 Google 服务条款，风险由 Chris 知情后决定 [待确认]
  - Reddit：官方 API 或公开 JSON 接口，搜 r/vancouver、r/VancouverFood
  - 小红书：MCP `search_feeds` + `get_feed_detail`
  - Yelp / TripAdvisor：暂时不做
- 笔记里不照搬别人的评价原文和照片（版权），用自己的话概括

## 评分规则（提案）
每条评价由 Jev 判断：
- `relevant` Noul：是否在评价这家店的真实用餐体验
- `ad_like` Noul：是否像软广、探店合作或刷评
- 口味 / 服务 / 性价比 / 环境 / 排队：每个维度一个 Choice {未提及, 差, 一般, 好, 很好}（「未提及」必须和「一般」分开）

之后在代码里计算：
- 评价权重 = P(relevant) × (1 − P(ad_like)) × 时间衰减（半年减半）
- 各维度分 = 提到该维度的评价加权平均 → **贝叶斯收缩**：(n·均值 + k·全市均值) / (n + k)，避免 3 条好评压过 300 条好评
- 每个来源先单独标准化（Google 普遍偏高），再跨来源加权
- 星级用 Google 的完整直方图（全体评价），不用抓来的样本 → 不会只看到好评
- 分歧度 = 各维度的方差，高分歧本身就是选题（「争议店」「避雷」）

## 每日流程（提案）
1. 选店：从候选池挑 3–5 家（代码规则 + 小红书近期热度）
2. 采集：Google / Reddit / 小红书
3. Jev 判断每条评价 → 代码汇总出餐厅画像
4. Claude 针对同一选题写 3–5 篇不同角度的草稿（榜单 / 单店深度 / 避雷 / 性价比）
5. Jev 审稿：每条事实性说法是否有采集数据支撑（citation check 模式）+ 合规 Noul（绝对化用语、引流、夸大）+ 表现预测分
6. 选稿：80% 选预测最高分，20% 随机探索 → 通知 Chris 审核（前期）→ MCP 定时发布
7. 回收：已发笔记在 24h / 72h / 7d 的数据；每周跑一轮 autoresearch 更新问题和写作指南
